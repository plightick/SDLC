# Apache Tika для проверки типа файла и извлечения текста

## Контекст и постановка задачи

Загружаемые файлы (PDF, DOCX, PPTX, TXT, PNG, JPG) нужно проверять по содержимому, а не по расширению (REQ-SEC-002), и извлекать из них текст для поиска (REQ-FUNC-013). Извлечение дорогое: большие файлы, возможны испорченные документы. Как выполнять эти операции?

## Драйверы решения

* Безопасность: файл с подменённым расширением не должен попасть в систему (REQ-SEC-002).
* Время загрузки файла 20 МБ не более 30 с (REQ-PERF-003).
* Устойчивость к повреждённым и «тяжёлым» файлам.

## Рассмотренные варианты

* Apache Tika: определение типа по содержимому синхронно, извлечение текста отдельной асинхронной задачей
* Apache Tika: определение типа и извлечение текста синхронно при загрузке
* Отдельные библиотеки под каждый формат (PDFBox, Apache POI)

## Итог решения

Выбранный вариант: «Tika, тип проверяется синхронно, текст извлекается асинхронной задачей», потому что проверка типа занимает доли секунды и должна отклонять файл сразу, а извлечение текста из документа на 20 МБ может длиться десятки секунд и не должно задерживать загрузку.

### Последствия

* Хорошо, потому что пользователь получает ответ на загрузку быстро; материал сразу идёт на модерацию.
* Хорошо, потому что один API на все форматы; Tika сама подбирает разборщик.
* Плохо, потому что материал некоторое время не находится поиском по содержимому (до минуты); пользователь видит статус «Индексируется».
* Плохо, потому что на ошибки разбора нужны таймаут (60 с) и повторная попытка.
* Нейтрально, потому что документы без текстового слоя (сканы) не индексируются, распознавание текста вне версии 1.0.

### Подтверждение

Прототип W-8 на 20 документах разных форматов с кириллицей до начала итерации 2 (REQ-POC-001); тест: файл `.pdf`, содержащий исполняемый код, отклоняется.

## Плюсы и минусы вариантов

### Tika, асинхронное извлечение

* Хорошо, потому что быстрый ответ и изоляция сбоев.
* Нейтрально, потому что нужна очередь задач (таблица и `@Scheduled`).

### Tika синхронно

* Хорошо, потому что проще кода.
* Плохо, потому что загрузка блокируется на время разбора и может превысить 30 с.

### PDFBox и POI

* Хорошо, потому что точный контроль над каждым форматом.
* Плохо, потому что отдельный код на каждый формат, больше работы; Tika использует эти же библиотеки.

## Дополнительная информация

Связанные требования: REQ-FUNC-003, REQ-FUNC-013, REQ-SEC-002, REQ-PERF-003. Представления SDD: 003-logical, 006-interaction, 008-patterns.
